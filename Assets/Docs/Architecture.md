# Архитектура прототипа

Только правила композиции: точка входа, инициализация сервисов, соглашения по коду.
Модель симуляции, параметры мира, дизайн-решения и история замеров сюда не входят.

## 1. Единая точка входа

`Bootstrap` — единственный MonoBehaviour, у которого есть `Awake` и `Update`.
Он владеет порядком инициализации и порядком кадровых вызовов.

Сцена — composition root. Все ссылки на сервисы выставляются только в инспекторе `Bootstrap`.
В коде нет `GetComponent`, `Find*`, статических синглтонов и сервис-локаторов.

Проводка намеренно не валидируется: если ссылка не проставлена, будет обычный
`NullReferenceException` при первом обращении. Стена проверок только маскирует поломку.

Кадровые вызовы идут из `Bootstrap.Update` в явном порядке. `Script Execution Order`
не используем: он живёт в настройках проекта, не виден в коде и действует на все сцены.

## 2. Сервисы

Сервис — постоянный объект, живущий всю жизнь сцены, в единственном экземпляре.

- Отдельный GameObject в корне сцены, имя совпадает с именем скрипта.
  Не вешать несколько сервисов на один объект.
- Зависимости приходят аргументами в `Initialize(...)`, а не через поля инспектора
  и не через `GetComponent`.
- Сервис не имеет `Awake`, `Start`, `Update`, `OnEnable`. Единственное исключение —
  `OnDestroy` для освобождения нативных ресурсов; он должен быть идемпотентным.
- Данные принадлежат одному владельцу. Сервис не хранит чужое состояние
  и не знает о внутренностях соседей.
- Публичные методы — только те, которые вызывает `Bootstrap`, плюс геттеры данных.

## 3. Соглашения по коду

- Комментарии и XML-документация — только на английском. Кириллица ломается в части
  инструментов и делает исходники нечитаемыми. Русский допустим в документации
  и в тултипах инспектора.
- Явные типы вместо `var`.
- Приватные поля — `_camelCase`; один публичный класс на файл; `sealed`, если не нужно
  наследование.
- `NativeArray` и другие нативные ресурсы освобождаются в `OnDestroy` сервиса-владельца.
